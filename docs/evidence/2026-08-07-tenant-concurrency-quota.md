# 租户并发配额，以及它在并发下确实成立的证明

日期：2026-08-07
主机：MacBookPro18,3 / Apple M1 Pro / 16GB / macOS Darwin 25.5.0

## 起因与一处对复审的更正

复审列出「尚无调用方认证和配额」。查证后：

**调用方认证是存在的。** 控制面以 OIDC 资源服务器运行，RS256 公钥验签、scope 校验、
tenant/application 声明，本地经 `SPRING_SECURITY_OAUTH2_RESOURCESERVER_JWT_PUBLIC_KEY_LOCATION`
接线（`devctl:349`）。这一条不准确。

**配额确实不存在。** 全系统唯一的并发上限是子代理准入的每父 8 个
（`JdbcSubagentAdmissionRepository:18`），那保护的是父 Run 不被自己的子任务淹没，
与「一个租户吃满平台所有 Worker 槽位」无关。任何租户可以无限建 Run。

## 实现的关键点

配额检查是**准入的一部分**，不是它之前的一步：

```sql
select max_active_runs from tenant_run_quotas where tenant_id = ? for update
```

先取租户配额行的行锁，再计数，再插入，全在同一事务。这与子代理准入锁父 Run 行是同一形态。
**配额行的存在就是为了被锁**——没有行的租户会先插入默认值，好让后续准入有东西可串行化。

**幂等重试不计入配额**：若该幂等键已对应一个 Run，调用方问的是它自己已经持有的容量。
否则一个重试超时请求的客户端会收到「你自己那个 Run」的配额错误，而那是最不该被要求退避的时刻。

拒绝用 **429 + Retry-After**，不是 400：请求本身没有任何问题，容量一空同一请求就会成功。
告诉客户端「请求有误」会让它去修一个没坏的东西。

## 并发实证

限额 2，四个线程同时创建（各自独立的 repository，必须在数据库里争抢而非共用一个事务模板）：

```
admitted = 2
refused  = 2
select count(*) from runs where tenant_id = ?  →  2
```

第三条断言是必要的：前两个是进程内计数器，它们可以同时正确而库里躺着三行。

## 门禁自证：去掉锁就失效

只把 `for update` 去掉，其余不动：

```
expected: 2
 but was: 4
```

四个并发请求**全部通过**，配额彻底失效。这正是「先数后插不够」的那个失败模式，
现在它有证据而不只是我的说法。锁已还原，还原后 151 用例全绿。

（注入时我第一次直接跑 `mvn -Dtest=...`，得到的是 `ExceptionInInitializerError` 而非断言失败——
集成测试需要 `run-java-tests` 注入的数据库环境变量。这个坑本会话踩过一次，又踩了一次。）

## 限制（明确不声称）

- **只做了并发配额。** Token 与费用配额未做——并发保护的是平台不被单个租户吃满，
  那两项保护的是账单，是不同的东西。
- 默认上限 64 写死在代码里，**没有 API 可以修改**它。租户级配置需要另一片工作。
- 计数只看 `queued/running/waiting_approval/suspended` 四个状态。若将来新增活动态而忘了
  加进这个列表，配额会**静默变松**——这是一个真实的维护风险，目前没有防护。
- 加权公平调度未做。配额只能拒绝，不能在多个租户之间排序。
- 未做 1000 Run 级别的压测，因此不声称配额在该规模下的行为。
