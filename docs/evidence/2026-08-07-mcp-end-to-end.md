# MCP 端到端：整条联邦链跑通

日期：2026-08-07
主机：MacBookPro18,3 / Apple M1 Pro / 16GB / macOS Darwin 25.5.0

## 链路

每一跳都是真实 socket，没有替身：

```
MCP 服务器（HTTP，loopback）
  ← 网关联邦客户端（JSON-RPC、解封、目录冻结）
  ← 网关 gRPC 服务端
  ← Worker gRPC 客户端
  ← 内核 Tool 注册表与审批闸口
```

前五片各自测自己那一跳。**这一条在任意一个接头出错时会失败**——这是「五个零件都在」
和「这东西能用」之间唯一能区分的东西。

## 一次跑通，五个断言

```
test a_federated_tool_is_discovered_registered_gated_and_called ... ok
（25.8 秒，其中绝大部分是 RSA-3072 密钥生成）
```

| 步骤 | 断言的事实 |
| --- | --- |
| 1. 发现 | 经网关从真实 MCP 服务器拿到 `mcp:search/web_search`，摘要是 64 位十六进制 |
| 2. 注册 | 转成 `SandboxClass::Federated` 的描述符并进入内核注册表 |
| 3. 闸口 | **配了租户豁免、参数也构造成能触发豁免**，计划仍是 `ApprovalRequired` |
| 4. 调用 | 批准后调用真的到达服务器，服务器自己的答案原样返回 |
| 5. 冻结 | 测试中途给服务器加一个工具，**同一次调用立刻被拒**，且该错误不可重试 |

第 3 步是整条链的安全属性：任何一处退化都会让它变成 `AutoApproved`。
第 5 步验证的是冻结**跨越整条链**成立，而不只是在网关内部成立。

## 故障注入：专打上一片明说没覆盖的那层

第五片的证据里我写过：「gRPC 层没有独立测试，翻译本身写错不会被发现」。
现在补上，注入两次都在翻译层：

| 注入 | 结果 |
| --- | --- |
| 响应里丢掉 `catalog_digest` | 端到端失败 |
| 转发一个空的 `frozen_catalog_digest`（等于废掉冻结） | 端到端失败 |

第二条尤其重要：**它不改任何规则代码，只让翻译层把参数丢掉**——
这正是「五个零件都对，接头把安全属性漏掉了」的形态。

## 一处刻意的不做

端到端用**明文 gRPC on loopback**，不走 mTLS。这个测试测的是联邦路径，
网关的传输安全另有覆盖。写在测试注释里而不是留给人推断。

## 明确不声称

- **测试用的 MCP 服务器是本仓写的**，实现 MCP 的一个子集。**没有对任何真实第三方
  MCP 服务器跑过。** 真实服务器的差异（SSE 响应、`Mcp-Session-Id` 会话、OAuth 授权）
  仍然全部未验证——这是本次 MCP 实现最大的未知。
- **Run 生命周期里没有自动发现。** 这条链需要调用方依次调 `list_tools` →
  `federated_tool_definitions` → `register_tool`。**Worker 的 assignment 路径还没有
  在 Run 开始时自动做这件事**，也没有把批准后的执行路由到 `call_tool`。
  能力齐了，自动接线没做。
- 端到端不含真实模型：没有模型建议一个联邦工具、再由内核发起审批的完整回路。
- 无 mTLS（见上）。
- 审批**发起**了，但没有验证批准之后内核会把执行交给谁——第 4 步是测试直接调的，
  不是内核调的。
