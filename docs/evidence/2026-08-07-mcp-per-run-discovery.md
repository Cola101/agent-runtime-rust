# MCP 收尾：Run 级自动发现与冻结

日期：2026-08-07
主机：MacBookPro18,3 / Apple M1 Pro / 16GB / macOS Darwin 25.5.0

## 一个在写这一片时才浮出来的设计错误

原计划是「Run 启动时把联邦工具注册进 Worker 的注册表」。写到一半发现这条路是错的：

**`ToolRegistry` 是 Worker 级的，而冻结目录是 Run 级的属性。**

两个 Run 对同一个服务器可以合法地持有不同摘要——一个在服务器改动前冻结，一个在之后。
名字为键的共享注册表只能装下其中一个。更糟的是同一 Worker 上第二个 Run 会拿到
`DuplicateTool` 错误，而那个错误它无论如何都处理不了。

改成：`discover_federated_tools()` **克隆** Worker 的注册表，把该 Run 的联邦工具加进副本，
返回这个副本。原生工具照旧共享，联邦工具按 Run 隔离。

用测试钉住：两个 Run 先后发现同一服务器，中间给服务器加了个工具，
**两个摘要必须不同**；且发现之后 Worker 自己的注册表**仍然认不出**那个联邦工具。

## 不可达的服务器：报告，不致命，也不消失

一台第三方服务器宕了，不应该让一个可能根本用不到它的 Run 失败。
但一个 Run 悄悄少了它被配置过的工具，会产生无法解释的执行记录。

所以 `FederatedRunTools.unavailable` 逐个记下服务器名和原因，交给调用方决定。
策略留在该决定它的地方，而不是埋在发现逻辑里。

同一个服务器内是**全有或全无**：半注册的目录会冻结一个描述了 Run 看不见的工具的摘要。

## 故障注入，以及一次诚实的空转

| 注入 | 结果 |
| --- | --- |
| 不可达服务器静默丢弃（不进 `unavailable`） | 失败 |
| `frozen_digests` 用 `or_insert` 代替 `insert` | **通过——这次注入是空转** |

第二条要说清楚：我想注入的是「跨 Run 共享状态」，但每次调用都新建映射、克隆注册表，
`or_insert` 和 `insert` 行为完全相同，所以这条注入什么也没测。

**Run 级隔离不是靠一行代码保证的，是靠函数签名**：`base_registry: &ToolRegistry`
是不可变借用，从类型上就不可能改到 Worker 的注册表。这比测试更强，
但也意味着**没有可以拆掉的那一行**——所以本文件不声称这条经过注入验证。

## 明确不声称

- **没有对任何真实第三方 MCP 服务器跑过。** 测试服务器是本仓写的，实现 MCP 的一个子集。
  SSE 响应、`Mcp-Session-Id` 会话、OAuth 授权**全部未验证**。这是本次实现最大的未知，
  排在任何后续工作之前。
- **批准之后的执行没有接进内核回路。** 内核会给出 `ApprovalRequired`，
  `call_tool` 也能调通，但两者之间没有代码——批准通过后由谁调用 `call_tool`、
  结果如何回到模型上下文，都还没有写。
- **`accept()` 没有调用发现。** 它是同步的而发现要走网络，所以自动接线的最后一步
  必须在异步调用方（Worker main / supervisor）里做，目前那里还没接。
- 没有真实模型建议一个联邦工具的完整回路。
- 无 mTLS 的端到端（见上一份证据）。
- 本地 stdio MCP 服务器不支持（ADR-0040 明写的取舍）。
