# `close_cancels_only_...` 在满并行下失败（2026-08-19）

**结论：不是这一轮那处循环修复造成的。** A/B 对照直接量过。
机制是这条测试自己的 1 秒界限扛不住 20 条测试满并行。**没有放宽它。**

## 为什么必须先怀疑自己

这条测试在**七次**门禁里从没挂过，然后在我改了驱动循环
（`Stop applying a Provider batch once the attempt has ended`）之后的门禁里挂了。
时间上完全吻合，而它改的又正是子代理会走的那条路径。

## A/B

只数这一条测试在**整个二进制**里挂了几次，别的测试挂不挂不影响这个计数
（去掉修复会让另外几条委托测试挂，所以不能按二进制整体成败比）：

| | 结果 |
| --- | --- |
| **带**这处修复，6 次整二进制 | close_cancels 挂 **6/6** |
| **去掉**这处修复，6 次整二进制 | close_cancels 挂 **6/6** |

**一模一样。和这处改动无关。**

单独跑这一条：**10/10 通过**，0.55 秒。

## 机制

| 并行度 | 结果 |
| --- | --- |
| `--test-threads=1` | 20/20 通过，22.2 秒 |
| `--test-threads=4` | 20/20 通过，13.0 秒 |
| 默认（按核数） | **必挂** |

失败信息自己说了：`the parent's next turn did not arrive within one second of the close`。
单独跑整条链路 0.55 秒，界限 1 秒——**余量 45%**，而它要在 20 条测试抢 CPU 时成立。

## 那它为什么过了七次门禁

没有确证。已经排除的：

- **不是这处修复**（上面的 A/B）
- **不是残留进程**。查到 11 个我这一 session 各次实验留下的 `agent-runtime-host`
  （含打包产物的两个、以及更早 worktree 里的一个 PTY supervisor），全部清掉之后
  仍然 4/4 挂。

剩下的解释有证据了：这台机器上常驻着**别的项目、别的会话**的 dev server。
停掉我自己那个之后再查，还有六个 vite 在跑（`ipm-deploy` 的几个 worktree，
端口 8580/8582/8584/8590 和另外两个）。**它们不是我的，没有去动。**

所以"安静的机器"在这里根本不存在，而环境负载随着旁边那些会话起落。
一条余量 45% 的墙钟界限在这种机器上时红时绿，与其说是偶发，
不如说是**它测的东西里混进了别人的负载**。

## 修法：把期限锚在它自己声称的那一刻

两个一秒是 `tokio::join!` **同时**起跑的，而真实顺序是串的：父收到关闭 → 子流被回收
→ 父发出下一轮。第三步的预算被前两步吃掉，**而失败信息说的是「关闭之后一秒内」**。

改成顺序等待：先确认子流回收，再从那一刻起给父一秒。这**确实允许了更多总墙钟时间**，
而这正是目的而不是副作用——它把「关闭之后 runtime 迟迟不继续」和「关闭期间机器很忙」
分开了，后者是这条断言从来不打算测的东西。

**6/6 挂 → 0/6 挂**（默认并行度，整个二进制，各跑 6 次）。

## 这条断言能看见什么、看不见什么

试图证明"它仍然抓得住真回归"时失败了，而这件事本身值得记下来：
在 `accept` 之前插 2.5 秒延迟，**测试照样通过**——父早就连上来了，连接躺在 TCP backlog 里，
晚一点 accept 也立刻返回。

所以它真正检查的是**父有没有在窗口内连上来**，是一条存活性断言，不是延迟断言。
改动前后都是如此。要把它变成延迟断言，得在 runtime 侧测量，而不是在这个测试恰好
持有的 socket 上测。

代码注释里原本写着「一个让父落后三秒的回归仍然会触发它」——**那句话我没能证明，已经删掉。**

## 没有做的事

- 没有放宽那个 1 秒界限。
- 没有把这条测试串行化。
- 没有把它记成 flaky 放过。

和 `one_thousand_runs_...` 是同一类：**一条墙钟界限，被写成测试的主题之外的兜底，
余量薄到在正常门禁负载下会翻红。** 该不该调是一个取舍——调了就接不住相应倍数的
真实回归——而那个取舍值得摆出来讲，不该由我顺手做掉。
