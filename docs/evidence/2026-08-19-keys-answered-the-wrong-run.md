# 快捷键回答的是另一个 Run 的问题（2026-08-19）

对话面的转录画的是**这段对话正在跑的 Run**，而它的审批快捷键绑的是
**「最近动过的那个 Run」**——这两个在很多时候不是同一个。

## 复现的条件（就是日常）

`shownRun` 与 `currentRun` 在一种情况下分道扬镳：

| | `shownRun`（转录用） | `currentRun`（快捷键用） |
| --- | --- | --- |
| 有选中的 Run | 那个 | 那个 |
| 打开着一段对话，它**没有**在跑 | **null** | 全局按 `updatedAt` 最新的那个 |

所以：在读一段已经结束的对话，另一段对话停在审批上——**按 `1` 就批准了屏幕上没有的那次工具调用**。
⌘I 打开的原始事件抽屉也是同一个错，抽屉头上还印着那个 Run 的 id，
于是两处互相矛盾的信息里，人会去信错的那一个。

`chat:cancel`（命令面板里的「停止当前 Run」）是同一个错，代价是取消。

## 守卫

从 registry 直接驱动，不经过窗口：

```
key 1 offers itself with no gate on screen: expected true to be falsy
```

不用 fixture 复现是有原因的——这个分歧取决于**恰好哪个 Run 最新**，
一个把「谁最新」摆好的 fixture 就是在断言它自己摆的东西。要钉住的是规则本身：
**一段没有 Run 在跑的对话，数字键没有东西可回答。**

## 修完之后，两条老测试的前提不成立了

它们不是被放宽的，是前提变了，而且**前提本来就写错了**：

`keys-reference.test.tsx` 里那句注释写着「没有选中任何东西，所以转录显示的就是正在跑的那个 Run」——
fixture 的默认对话 `activeRunId` 是 `null`，**这句话是假的**。它一直靠 `currentRun` 的
「全局最新」凑出正确答案。现在把 `{ activeRunId: RUN_LIVE }` 明写出来，
注释说的和 fixture 给的才是同一件事。

命令面板那条同理：它拿「停止当前 Run」当过滤用的样本，而默认 fixture 里这段对话没有 Run 在跑，
命令**正确地**不出现。改成开一段自己的 Run 在跑的对话。

顺带补了一条：对话没有 Run 在跑时，命令面板里不该出现「停止当前 Run」。

## 这个错是怎么活下来的

`currentRun` 和 `shownRun` 的第一个分支一模一样（都先看 `desk.selected`），
所以任何**先点一个 Run 再操作**的测试都分不开它们。分得开的只有
「打开一段对话，而它没在跑」，而这恰恰是最日常的一种停留。
