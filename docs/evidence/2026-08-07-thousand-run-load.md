# 1000 Run 压测：配额、公平派发在规模下的实测

日期：2026-08-07
主机：MacBookPro18,3 / Apple M1 Pro / 16GB / macOS Darwin 25.5.0

## 为什么必须做

在此之前，配额和公平派发都只在个位数行上验证过。**一个会重复计数的配额和一个
平方复杂度的排空，在 4 行数据上看起来完全一样。** 尤其是上一片刚给公平派发留了一个
明说的未知数：排名对每次轮询的**全部**可领取行计算，代价随积压增长。

## 测什么

10 个租户 × 100 个 Run = 1000，8 个写线程并发，各持自己的 repository（必须在库里争抢）。
其中 1 个租户权重 4，其余权重 1——公平性要在数字里看得见，不能只断言「集合里都有」。

## 实测

```
load: 1000 runs admitted by 8 writers in 2669 ms (375 runs/s);
      drain 10 claims of 100, slowest 14 ms, first claim 11 ms
load: first batch shares {…=31, …=8, …=8, …=8, …=8, …=8, …=8, …=7, …=7, …=7}
```

三件事各自成立：

**准入 375 Run/秒。** 每个 Run 都走了完整准入：锁租户配额行、数活动 Run、
查 24 小时消费窗口、插 Run、插 Outbox，全在一个事务里。准入按租户串行化是设计使然，
10 个租户就是并行度上限，所以这个数字是「10 路串行准入」的吞吐，不是理论上限。

**排空最慢 14 毫秒。** 这就是上一片留下的那个未知数的答案。1000 条积压下，
带部分索引的全量排名是 14 毫秒。**不构成问题，因此不做按租户 lateral 取头部的优化。**
只在 1000 这一个量级测过，不向上外推。

**权重按 4:1 分。** 首批 100 条里，权重 4 的租户拿 31，其余各 7–8。31 / 7.7 ≈ 4.0。
这是在 1000 条积压、10 个租户同时竞争下测的，不是两个租户的玩具场景。

## 断言而不是打印

数字是打印的，但通过与否由断言决定：

| 断言 | 挡住什么 |
| --- | --- |
| `count(*) from runs = 1000` | 进程内计数器可以两个都对而库里是另一个数——配额 bug 正是这种形态 |
| 首批租户数 = 10 | 旧 FIFO 下 1000 条积压里取 100 条**可能全是一个租户的** |
| 权重 4 的份额 > 其他租户份额 × 2 | 只断言「都在」的话，1:1 也通过 |
| 单次领取 < 2 秒 | 不是性能指标，是**平方复杂度的绊线**——真出问题会超出几个数量级而不是几个百分点 |

2 秒这个阈值刻意给得宽。测出来是 14 毫秒，留了 140 倍余量；把阈值卡在 20 毫秒
只会换来一条随机器负载抖动的假红。

## 顺带消掉的重复

写压测时我复制了一份 `seedResourceChain`（60 行的资源链播种）。两份会漂移，
而漂移的那份日后失败的原因会和它本来要检查的东西毫无关系。已提成
`ResourceChainFixture`，两个测试类共用。

## 检查结果

```
Java（run-java-tests）  159 通过 / 0 失败 / 1 跳过
压测单跑                 3.5 秒
```

3.5 秒，所以它**留在常规套件里**，是每次都跑的门禁，不是一次性脚本。

## 明确不声称

- **范围是控制面：准入、Outbox、排空。** 它**不执行** Run，因此对 Worker 吞吐、
  模型延迟、端到端时延一个字都没说。任何人不得把 375 Run/秒读成端到端吞吐。
- 单机单 PostgreSQL 实例，无副本无连接池调优。这是开发机的数字，不是生产容量规划依据。
- 只测了 1000。没测 10,000，因此不声称在该量级下排名代价仍可接受。
- 没有测**持续负载**：这是一次性灌 1000 条然后排空，不是稳态到达率下的排队行为。
