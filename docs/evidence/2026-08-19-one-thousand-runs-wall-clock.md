# 那条墙钟测试为什么红（2026-08-19）

> **这份文档的第一个结论是错的，下面第三节推翻了它。**
> 我的 dev server 确实有影响，但它不是主因。

`one_thousand_runs_keep_hot_state_recovery_and_process_resources_bounded`
在今天第三次全量门禁里挂了：**187.09s / 界限 180s**，超 4%。
前两次门禁它都过了。

## 不是回归

同一次失败里，它的**资源断言全部通过，而且余量很大**：

```
runs=1000 hot_run_directories=16 tombstones=984 state_files=70
recovery_scan_ms=574 rss_peak_bytes=29130752 fd_peak=37 fd_final=12
elapsed_ms=187094
```

热目录 16、fd 峰值 37、RSS 峰值 29MB、恢复扫描 574ms ——
这条测试真正要守的东西一条没破，破的只有那个墙钟数。

## 是我

查这台机器上在跑什么，找到**三个我自己留下的 vite dev server**，
都在这个仓库的 `.claude/worktrees/wf_*` 里，是我早先几次 workflow 的 agent 起的，
起于 21:36–22:31，一直跑到 05:30。**今天每一次门禁都被它们压着。**

（另外还有六个 `ipm-deploy` 的 vite，那些是别的会话的，没有动。）

停掉我自己那三个之后，同一条测试单独跑，**五次**：

| | 用时 |
| --- | --- |
| 1 | 159.57s |
| 2 | 156.50s |
| 3 | 157.46s |
| 4 | **166.25s**（最坏） |
| 5 | 159.63s |

界限 180s。最坏一次余量 7.6%。**没有改这个界限，没有串行化，没有删断言。**

## 然后我又犯了一次同样的错

写完上面这段之后不到十分钟，我在门禁跑到 `one_thousand_runs` 的**同时**
跑了一遍 vitest（15 秒、29 个文件）。那次它挂在 **183.13s** —— 超界限 3.13 秒。

三个数据点摆在一起，机制就没有别的解释了：

| 机器上还有什么 | 用时 |
| --- | --- |
| 三个我留下的 dev server | **187.09s** ✗ |
| 一遍 vitest（15 秒） | **183.13s** ✗ |
| 什么都没有（五次） | 156.5–166.3s ✓ |

**一遍 15 秒的前端测试就够把它推过界。**

## 该记住的

1. **做视觉验收要开 dev server，那就别同时跑门禁。** 这次是我自己踩的：
   为了看新那行长什么样开了 preview，然后在它还开着的时候起了门禁。
2. **workflow 用 worktree 隔离时，agent 在里面起的 dev server 不会被清掉。**
   worktree 本身会自动删，里面的进程不会。这是一个我以后每轮都该查的东西。
3. 这条界限**余量约 12%**，仍然是三条薄界限之一。这次不是它的问题，
   但它下次仍然会先于任何东西翻红——那个取舍还摆在那里，没有替谁做掉。

`2026-08-19-close-handshake-under-parallelism.md` 里写着"这台机器上常驻着别的会话的
dev server"，那句话当时是对的，**但不完整**：其中一部分是我自己的。


## 三、上面那个结论是错的：主因是同一个二进制里的兄弟测试

写完前两节之后又红了一次（门禁里 188.34s），而那一次我**什么重活都没跑**。
所以做了决定性对照：**把整个 `embedded_retention` 二进制单独跑一遍**，
没有别的 cargo 活，我的 dev server 早就停了，机器负载还在往下走。

```
1000 runs took 189.770027667s
test result: FAILED. 12 passed; 1 failed
```

四组数摆在一起：

| 怎么跑 | 用时 | 结果 |
| --- | --- | --- |
| **只跑这一条**（五次） | 156.5 / 157.5 / 159.6 / 159.6 / 166.3s | ✓ |
| **整个二进制单独跑** | **189.8s** | ✗ |
| 门禁里，我另外跑了 vitest | 183.1s | ✗ |
| 门禁里，我留着三个 dev server | 187.1s | ✗ |
| 门禁里，我什么都没跑 | 188.3s | ✗ |

**第二行推翻了第一节的结论。** 主因不是我的负载，是
`embedded_retention` 这个二进制里**另外 12 条测试和它并发**——其中
`multi_tenant_multi_workspace_churn` 也是一条重的，门禁日志里两条同时打出
"has been running for over 60 seconds"。

我用 `--test embedded_retention one_thousand_runs` 单独量，恰好把这 12 条兄弟滤掉了，
于是量出来的是一个**任何门禁都不会出现**的场景。**用错误的方式测量，得到了一个好看的数。**

我的 dev server 确实有影响（那三个跑了八小时的东西该清），
但把红归给它们是**下早了的结论**，而且是靠一个不成立的对照做出来的。

## 该怎么说这件事

不是"偶发"，是**这条测试在它自己的二进制里跑不进 180 秒**——而那正是每一次门禁跑它的方式。
它只在被单独挑出来跑的时候过。

**没有改这个界限。** 摆在这里的取舍是：

- 界限设在 180s，而真实门禁下它稳定在 183–190s → **每次门禁都红**，这不是回归信号，是噪声。
- 放宽到（比如）240s → 它就接不住一个"慢 33%"的真实回归。
- 或者把它从共享二进制里挪出去（单独一个 test target），让墙钟量的是它自己 →
  那样 180s 有 12% 余量，但它测的东西**变了**：从"门禁负载下 1000 个 Run"变成"独占机器时 1000 个 Run"。

三条路都要人来选，我一条都没有替你走。资源断言（热目录 16、fd 峰值 37–38、
RSS 峰值 28MB、恢复扫描 577–597ms）在**每一次**运行里都通过，余量 30–90 倍。
