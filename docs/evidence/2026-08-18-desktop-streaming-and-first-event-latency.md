# 桌面流式事件与首个事件延迟证据（2026-08-18）

## 复核事实

| 边界 | 修改前 | 风险 |
| --- | --- | --- |
| 转录更新 | 每 1.2 秒重读整段日志 | 无论 Runtime 多快写出来，屏幕都按 1.2 秒量化；一段回复要么整段出现，要么等下一拍 |
| 生命周期 | 来自 cursor 的类型化边界 | **必须保持如此** —— 从"收到的最后一条事件"推断 Run 结束，恰恰在日志被回收、宿主被替换、Run 停在人身上时出错 |
| 每个 Run 的首个事件 | 未测过 | 桌面开发时"按下回车后 7 秒没反应"，此前无人量过是什么 |

## 实现结果

- `watch()` 是**独立于 `call()` 的函数**，不是给 `call()` 加一个可选参数。`call` 有截止时间，因为
  不回答的请求是坏掉的 Runtime；watch 没有，因为一分钟不说话的 Run 是在思考。
  可选的截止时间正是"请求永远等下去"的来源。
- 流由 daemon 自己终止（终止边界 / 历史被回收 / 错误），客户端**从不判断 Run 何时结束**。
- 合并按 **sequence**，不是追加：轮询和流本来就重叠，sequence 让重叠无害。
- **事件走流，边界仍走 cursor**。`withStreamed` 重投影文本、工具调用与用量，
  但原样保留 cursor 报的 `lifecycle`。
- 只跟随**正在跑的那一轮**（当前会话 head 指名的那个）。跟随所有 Run 会为没人看的日志各占一条连接。
- 轮询读到的部分会从流的暂存里清掉，避免它长成日志的第二份副本。

## 可执行门禁

| 门禁 | 结果 |
| --- | --- |
| `vitest run` | 48 passed |
| 流上的终止事件不得决定 Run 结束 | 打破后变红 |
| 按 sequence 去重 | 打破后变红 |

**其中两条我第一次写错了。** 「终止事件」那条被无关文本满足（`/在跑|运行/` 匹配到了别处），
「去重」那条数的是元素个数——而重复文本会并进同一个段落，个数不变。两条都改成断言**具体文本**后，
打破才真的变红。第一次的打破全绿，说明它们当时什么也没守。

## 每个 Run 的首个事件：7.5 秒是怎么来的

用文件时间戳定位：`run.json` 在 **2.3ms** 落盘，`events.jsonl` 第一条在 **7520ms**。
`sample` 采样守护进程，叶子是 `agent_tool_runtime::digest_file`。

机制：`TrustedNativeExecutor` 构造时对受信工具二进制做全量 SHA-256，而**每个 Run 新建一个 Host**。
debug 二进制 64MB，debug 版 sha2 未优化。

| 构建 | 二进制 | 首个事件 |
| --- | --- | --- |
| debug | 64MB | 7.5s（三次测量一致） |
| release | 20MB | **230ms**（三次） |

**这不是产品缺陷，是开发体验陷阱。** 摘要本身是真实安全属性（`ExecutableChanged`），
不该被"优化掉"。记在这里，是为了下次有人看到 7 秒时不必重新做一遍定位，
也为了没人把它当成可以删掉的开销。

## 仍然没做

- 流的收益受 provider 自身速度限制：stub 的整段回复只要 120ms，落在一个轮询周期内。
  真实差别在**首字延迟**（写出来即到达，而不是最多晚 1.2 秒），以及慢 provider 下的逐字出现。
- 轮询仍在跑，负责列表、边界与未被跟随的 Run。
